How to Speed Up WordPress: Diagnose First

Nearly every WordPress speed guide hands you the same list of tactics regardless of what's actually wrong with your site. This one starts with three measurements that tell you which of three problems you have, because the fix for each is different and the wrong one costs you months.

  2. What the numbers actually mean
  3. Three diagnosis profiles

Start by measuring

Almost every WordPress speed checklist you'll find is a list of tactics in a fixed order: install these plugins, convert your images, add a CDN. The problem is that the tactics aren't interchangeable. If your bottleneck is a slow server, image optimisation changes nothing. If your bottleneck is a 4 MB hero image, upgrading your hosting plan wastes a year of subscription fees.

So measure first. Three tools cover most of what you need:

  • PageSpeed Insights — gives both lab data (a simulated load) and field data (real Chrome users, once you have enough traffic). The field data is the honest one.
  • WebPageTest — produces a waterfall showing exactly which resource blocks which, and when. The best tool for finding the specific culprit.
  • Query Monitor (plugin) — shows slow database queries, the hooks firing on a page, and PHP errors. The best tool for problems that originate in your own code.

Run the same page three times and take the median. Single runs are noisy, especially on shared hosting where your neighbours' traffic affects the result.

What the numbers actually mean

Four metrics matter, and they point at different causes:

MetricWhat it measuresGoodWhat a bad score usually means
TTFBHow long until the server sends the first byteUnder 600 msServer-side: no caching, slow queries, insufficient PHP workers
LCPWhen the largest visible element finishes renderingUnder 2.5 sHero images, render-blocking CSS and JS, slow server response
INPHow quickly the page responds to interactionUnder 200 msToo much JavaScript running on the main thread
CLSHow much the layout shifts while loadingUnder 0.1Images or ads without dimensions, fonts swapping, injected banners

INP replaced First Input Delay as a Core Web Vitals metric, so older guides still reference FID — if you're reading something that optimises for FID, it's out of date. The practical difference is that INP measures responsiveness across the whole session rather than just the first interaction, which makes it harder to game and more representative of how a site actually feels.

Three diagnosis profiles

Compare your TTFB against your LCP. That single comparison tells you which of three problems you have.

Profile 1: High TTFB, acceptable LCP

The content renders quickly once it arrives, but the server takes too long to start sending it. This is a server-side problem: no page caching, slow database queries, no object cache on a dynamic site, or too few PHP workers for your concurrency. Plugins that optimise images and JavaScript will do nothing here. Look at caching, query performance, and capacity.

Profile 2: Fast TTFB, slow LCP

The server responds quickly, then the browser spends seconds assembling the page. This is a front-end problem: oversized images, render-blocking scripts and stylesheets, heavy page-builder output, web fonts. Upgrading hosting will do nothing here. Look at images first, then JavaScript and CSS delivery.

Profile 3: Fine LCP, poor INP

The page looks ready, then feels sluggish when you click. Almost always too much JavaScript on the main thread — page builder runtime, several analytics tags, chat widgets, sliders and animation libraries all competing. Look at what's loading, not at your server.

A fourth pattern worth naming: good LCP and INP but bad CLS means things are moving around as the page loads. That's usually images without width and height attributes, or a font that swaps in late and reflows the text. It's the least technically serious of the four and the most irritating to actually use.

Fix things in this order

Once you know your profile, work through the fixes ranked by impact per unit of effort.

1. Images (usually the single biggest win)

For most sites this is where the seconds are. Export images at the size they're actually displayed — a 300 px-wide blog column doesn't need a 4000 px original. Convert to WebP or AVIF. Lazy-load anything below the fold. Always set width and height attributes so the browser reserves space and your CLS doesn't suffer.

2. Page caching and browser caching

Serving stored HTML instead of rebuilding the page on every request is the largest available win for anonymous traffic. Check whether your host already does this before installing a plugin — our caching plugins guide covers the four layers and how to avoid stacking two page caches.

3. Trim the front end

Deactivate and delete plugins you aren't using — disabled plugins still sit on disk, but active ones run code on every request. Delay non-critical JavaScript, remove unused CSS on pages that don't need it, preload your most important asset, and make sure fonts use font-display: swap.

4. Clean the database

Post revisions, expired transients and orphaned tables left by deleted plugins accumulate for years. The effect is modest on a small site, but on a large one it slows admin screens and backups noticeably. Take a backup first, then clean.

5. Put a CDN in front of static assets

Worth doing, and often free, but be clear about what it does: it cuts the time to fetch images, CSS and JS from locations near your visitors. It does not make your server build pages faster.

6. Change hosting — last, not first

Do this only if your TTFB is the bottleneck and steps 1 to 5 haven't moved it. It's the most expensive lever and the one most often pulled prematurely.

Resist the plugin pile. Advice that opens with "install these twelve optimisation plugins" has it backwards. Every plugin is code that runs on your server. A lean site on decent hosting beats a bloated site running five overlapping optimisers every time.

When hosting genuinely is the problem

Hosting is the right lever when your measurements point at the server and you've already cached what can be cached. Three situations where that's genuinely true:

  • Your TTFB is high on cached pages. If a page served from cache still takes a second to start responding, the server or the network path is the constraint, not your code.
  • Performance collapses during traffic spikes. Fast when you test it, unusable during a campaign. That's a concurrency ceiling — PHP workers — and no amount of front-end optimisation changes it.
  • Logged-in and dynamic pages are slow, anonymous pages are fast. That's the signature of a site whose cache is doing the heavy lifting while the server can't handle uncached requests. Common on stores and membership sites.

If you've reached this point, the honest comparison isn't "which host is fastest" — it's which host allocates the resources your specific profile needs. A host that gives you generous PHP workers and Redis object caching will outperform a nominally faster host that throttles you at the plan level. FAQ

Is a 100/100 PageSpeed score the goal?

No, and chasing it often makes sites worse. The lab score is a simulated load on one device under one set of conditions. Field data — how real Chrome users actually experience your site — matters more, and it only appears once you have meaningful traffic. A site scoring 78 with good field data is in better shape than one scoring 98 in the lab while real users on mid-range phones wait four seconds.

Does a CDN fix a slow server?

No. A CDN places static files like images and CSS close to your visitors, which shortens download time. It does nothing about how long your server takes to build the page in the first place. If your TTFB is 1.5 seconds, a CDN leaves it at 1.5 seconds while delivering the images that follow slightly faster. It's a genuine improvement, just not the one people expect.

Will a caching plugin fix everything?

It fixes one specific problem — the cost of regenerating HTML for every visitor — and does nothing for oversized images, render-blocking JavaScript, third-party scripts, or a server that runs out of capacity under load. It's usually the highest-value single change on an uncached site, and usually the least relevant change on a site that's already cached at the server level.

How fast is fast enough?

Google's Core Web Vitals thresholds for 'good' are LCP under 2.5 seconds, INP under 200 milliseconds, and CLS under 0.1. Those are reasonable targets. Below them, the returns on further optimisation drop sharply for most sites. Getting LCP from 4.0s to 2.4s changes real business outcomes; getting from 1.8s to 1.4s usually doesn't.

Do I need to upgrade my hosting?

Only if your measurements say the server is the bottleneck. The test is simple: enable page caching, then measure TTFB on a cached page. If it's still slow, the server is your problem. If it's fast, your problems are elsewhere and a hosting upgrade will cost you money without changing what your visitors experience.

Why is my site slow in the evening but fine in the morning?

Usually contention. On shared hosting you're pooling CPU, memory and PHP workers with other sites, and evenings are peak time for everyone. It can also be your own scheduled tasks — backups, cron jobs and import scripts often run overnight or in the evening. Check whether your host's resource graphs spike at the same time your site slows; that distinguishes the two causes quickly.
