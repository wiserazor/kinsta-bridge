WordPress Site Down: How to Diagnose It

Your site won't load. Before you open a support ticket or restore a backup, find out which layer is actually broken. A DNS failure and a database failure can look identical in the browser and have nothing in common underneath, so this guide works outward from the network towards WordPress, in the order that narrows it down fastest.

Work out which kind of "down" you have

"Down" covers several different failures, and the symptom is the fastest route to the layer. Open the site and note exactly what you see before you touch anything:

  • The browser can't connect at all ("This site can't be reached", "Server not found"): the name isn't resolving, or nothing is answering at the other end.
  • A status code instead of your site (500, 502, 503, 504): the server is reachable and failing behind the front door.
  • A certificate warning instead of your site: the site may be perfectly healthy and only TLS is broken.
  • An unstyled page, or a redirect loop: WordPress is running, so the fault is inside the application layer.
  • It loads for others but not for you: your network, your DNS cache, or a regional block. Not the server.
  • The front end is fine but /wp-admin isn't (or the reverse): almost always application-level. A server problem takes down both.

Also write down when it started and what changed just before. A site that broke minutes after a plugin update, a nameserver change, or a PHP version bump has already pointed at the answer.

Rule out your own connection first

Two minutes here can save an hour of server troubleshooting. The goal is to establish whether the site is down for everyone or only for you.

  • Try a different network. Mobile data instead of Wi-Fi, or the reverse.
  • Check from outside your own network. Any multi-location uptime checker will tell you whether the failure is global. If a checker in three regions loads the page and you don't, the problem sits between you and the site.
  • Flush your local DNS cache, because a cached record keeps sending you to an address that may no longer exist. On Windows, run ipconfig /flushdns in a command prompt. On macOS: sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder.
  • Open an incognito window to rule out a cached response or an extension.
A regional network problem looks exactly like a server outage. If you sit behind a corporate network, a restrictive national firewall, or a VPN that has just changed exit node, the site can be perfectly healthy everywhere except from where you are. Cross-check from an external monitor before you email your host about an outage that isn't happening.

Layer 1: Does the domain resolve?

Start at the outermost layer. Can the name be turned into an address?

dig +short yourdomain.com
dig +short NS yourdomain.com

If dig isn't installed, nslookup yourdomain.com gives you the same answer on Windows.

What you're looking for:

  • No A record at all: the DNS zone is broken or the record was deleted. Nothing further down this page matters until that's fixed.
  • An A record pointing somewhere unexpected: the domain may have been moved, or the DNS changed by someone else.
  • NS records still pointing at the registrar's defaults: the host was never given authority over the zone, so whatever you configured in the hosting panel was never live.
  • Correct records, but your browser disagrees: cached DNS, covered above.

Two failures deserve a specific check because they present as "the host is down" when the host is fine:

  • An expired domain. If the registration lapsed, DNS stops resolving entirely and no amount of server troubleshooting will help. Check the expiry date at your registrar before going further.
  • A recent DNS change. Records propagate according to their TTL, which ranges from five minutes to 48 hours. If you changed nameservers or an A record in the last day, you may simply be waiting. Our migration guide covers how to plan that window.

You can also bypass DNS completely. If you know the server's IP address, request the site directly from it:

curl -I https://SERVER_IP -H "Host: yourdomain.com" -k

If that returns your site but the domain doesn't, the problem is DNS and not the server. That single test splits the whole investigation in two.

Layer 2: Is the server answering?

Next, check whether anything is listening. One command gives you both the status and the failure mode:

curl -sS -o /dev/null -w "%{http_code}\n" https://yourdomain.com
  • A number (200, 403, 500, 502): the server answered. Go to the layer that code belongs to.
  • Connection refused: nothing is listening on that port. The web server is down, or the port is closed.
  • Connection timed out: packets are going nowhere. Usually a firewall, a dead host, or a blocked IP.
  • Could not resolve host: back to Layer 1.

Then check the two things people forget, in this order:

  1. Your host's status page. If it reports an ongoing incident, stop troubleshooting. Waiting is the fix, and nothing you change will help.
  2. Your account status in the hosting panel. This is the most common cause of a sudden, unexplained outage that has nothing to do with the server: a suspended account. Suspensions come from an expired card, a failed renewal, exceeded disk or bandwidth limits, or an abuse report. The server is perfectly healthy; your access to it isn't. Check billing and resource usage before anything else.

Note that ping proves very little here. Many hosts block ICMP, so an unreachable ping alongside a working site is normal, and a successful ping says nothing about whether the web server is up.

Layer 3: Is the certificate valid?

If the browser shows a warning page rather than your site ("Your connection is not private", NET::ERR_CERT_DATE_INVALID), the certificate is the problem. It's the most common cause at this layer and the easiest to confirm:

echo | openssl s_client -connect yourdomain.com:443 -servername yourdomain.com 2>/dev/null | openssl x509 -noout -subject -dates

That prints the name the certificate was issued for and its validity window. Two fields matter:

  • notAfter in the past: expired. Automatic renewal failed at some point.
  • subject naming a different domain: the certificate doesn't cover the hostname being requested. This happens when a subdomain was added without a matching certificate, or when the host's temporary certificate is still in place.

Free certificates renew automatically, and the usual reason they stop is a change that broke the validation method: DNS moved away from the provider, a proxy was switched on, or a .well-known path stopped being served. Reissuing from the hosting panel normally clears it.

One combination is worth recognising, because it sends people down the wrong path: if http:// loads and https:// doesn't, the site itself is fine and only TLS is broken. Don't go looking for a database problem.

Layer 4: Gateway errors (500, 502, 503, 504)

The server is reachable and TLS works, but the response is an error. This is the layer where the request arrives and the thing behind it doesn't answer:

  • 502 Bad Gateway: the web server asked PHP for a response and got nothing valid back. A crashed or exhausted PHP process pool is the usual cause.
  • 503 Service Unavailable: the server is deliberately refusing traffic, whether from overload, maintenance mode, or a resource limit being enforced.
  • 504 Gateway Timeout: PHP accepted the request and then took too long. Something in the stack is hanging, often a plugin waiting on an external API or an unbounded query.
  • 500 Internal Server Error: most often a fatal PHP error or a broken .htaccess. A 500 is usually the same underlying problem as a blank page, with the error finally surfacing. Our white screen guide covers that diagnosis step by step.

If a CDN or proxy sits in front of your site, add one more possibility: the CDN is up and your origin server is not. CDN error codes name this precisely (521, 522, 524, 525 and 526 at Cloudflare), and they all mean the same thing, namely that the edge could not get a valid answer from the origin.

Two checks are worth running at this layer:

  • Read the error log. A 502 accompanied by Max children reached, or a 500 followed by Allowed memory size exhausted, is a specific and fixable problem rather than a mystery. When something is down, the error log is the highest-value file on the server.
  • Look at resource usage. If the outage coincides with a traffic spike, PHP workers or database connections may have been exhausted rather than broken. Our PHP workers guide explains why that shows up as a wall rather than a gradual slowdown.

Layer 5: Is WordPress itself running?

Everything above can be healthy while WordPress itself is broken. Two failure modes account for most of it.

"Error establishing a database connection" means PHP is running and reached the database step. Check in this order: the credentials in wp-config.php, whether the database server itself is up, and whether the connection limit has been reached. On managed hosting the second and third are your host's side of the fence, but verifying the first takes a minute and rules out the most common cause, which is a hostname or password that changed during a migration.

A blank page or a partial load means PHP is failing inside WordPress. That is the white screen guide's territory, and the diagnosis there starts by making WordPress write the fatal error to a log instead of hiding it.

Three further checks are worth running when the failure has no obvious pattern:

  • .htaccess. A single bad line breaks the whole site, and an interrupted write leaves the file truncated. Renaming it to .htaccess.bak tests this in seconds on Apache. If the site comes back, that file was the problem.
  • The active theme. A fatal error in a theme takes down the front end while leaving wp-admin reachable, which is a useful clue in itself.
  • PHP version. A site that broke immediately after a PHP upgrade is almost always running code that calls a function the new version removed.
Take a backup before you start changing files. You need the database and wp-content, and those two contain your entire site. If you can't reach wp-admin, pull the copy through your host's file manager or over SFTP. Our backup guide explains why a host snapshot is usually the fastest route back.

Contacting your host with evidence

Once DNS resolves, an external checker agrees the site is down, and the server returns a 5xx, the problem is on your host's side. That is the point at which a support ticket is the right move, and the quality of the ticket decides how quickly it gets solved.

Send this:

  • the domain name and the exact time the problem started, with your timezone
  • what you see, described in the browser's own words
  • the output of the status code check above
  • anything relevant from the error log
  • what you have already ruled out

A ticket that says "my site is down, please fix" gets a reply asking for information. A ticket that says "example.com has returned 502 since 14:20 UTC, DNS resolves correctly, an external checker confirms the failure from three regions, and the error log shows Max children reached" gets an engineer.

That difference is also a fair way to judge a provider. Every host goes down occasionally, and what separates them is whether support reads the ticket and answers with something specific, or replies with a template asking you to clear your cache. If you are comparing hosts, look at how each one describes its own incident response before you need it, not after. Our hosting comparison covers that alongside the specifications.

FAQ

How do I tell whether the problem is my host or my WordPress site?

Use the status code as the dividing line. Connection failures and gateway errors (502, 503, 504) belong to the host's infrastructure. A page that returns 200 but renders blank, or a site that loads with database errors, belongs to WordPress. If external checkers in several regions can't reach the site at all, the problem is on the host's side regardless of what WordPress is doing.

Why does my site load for everyone except me?

Almost always something local: a cached DNS record, a cached browser response, a VPN exit node, or a network-level block. Flush the DNS cache, try a different network, and check the site from an external monitor. If the monitor sees the site, the site is up and the problem is on your side of the connection.

How long does DNS propagation actually take?

It follows the TTL on the record you changed, not a fixed schedule. Anywhere from five minutes to 48 hours is realistic. The standard way to make a planned change fast is to lower the TTL a day in advance, so the old record expires quickly once you switch.

Can a single plugin take the whole site down?

Yes. A fatal error in a plugin takes down every page that loads it, which on most sites is all of them. The tell is that deactivating plugins brings the site back immediately. If you can't reach wp-admin, you can deactivate them externally by renaming the plugins folder over SFTP, which the white screen guide covers in detail.

What's the difference between a 502 and a 504?

A 502 means the web server asked PHP for a response and got nothing valid back. A 504 means PHP accepted the request and never finished in time. Both point at the PHP layer, but a 504 usually means something is slow rather than dead, which is why it often turns out to be a plugin waiting on an external service.

My site went down right after I changed the nameservers. Is it broken?

Probably not. That's expected propagation. Confirm the records are correct at the new provider, wait out the TTL, and resist the temptation to change something else while you wait. Changing things twice during propagation is how a routine migration turns into a genuine outage.
