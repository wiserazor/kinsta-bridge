Move WordPress to a New Host Without Downtime

Migrations fail in two ways: downtime from switching DNS before the new site works, and email that dies silently three days later. Both come from the same mistake - pointing visitors at the new server before it's ready. Here's the sequence that avoids them.

Why migrations go wrong

Site migrations fail in two ways, and they're opposites.

The first is downtime that shouldn't have happened: you copy files, switch DNS, and then discover a problem — a missing database table, a broken URL, an SSL certificate that hasn't been issued — while visitors are already hitting the new server. You're now debugging live.

The second is email silently dying. This one is worse, because it doesn't announce itself. The site looks perfect, and three days later you realise nobody has received an enquiry since the move.

Both are avoidable with the same principle: get the site fully working on the new host before anyone is pointed at it. Everything below follows from that.

Phase 1: Prepare (do this a day early)

  1. Take a full backup. Database and wp-content. Verify you could restore it — our backup guide covers testing a restore properly.
  2. Write down what's running. Every plugin, any custom code, cron jobs, integrations, and where your DNS currently points. You'll want this list when something behaves differently afterwards.
  3. Lower your DNS TTL. This is the step people skip and then regret. TTL (time to live) tells resolvers how long to cache your DNS record. If it's 14400 seconds (4 hours), some visitors will keep hitting the old server for hours after you switch. Set it to 300 seconds at least 24 hours before the migration, so when you do switch, propagation takes minutes rather than a day.
  4. Inventory your DNS records. Screenshot everything — A, CNAME, MX, TXT, SPF, DKIM, DMARC. Especially the mail records.

Phase 2: Build the site on the new host

Set up the site on the new host while the old one keeps serving visitors. Don't touch DNS yet.

Three ways to get the files and database across:

  • A migration plugin (All-in-One WP Migration, Duplicator, Migrate Guru) — the accessible option. These handle the URL replacement problem for you, which is the main reason to use one if you're not comfortable on the command line.
  • Manual copy — export the database, copy wp-content over SFTP or with rsync, import the database on the new host. Fast and reliable for large sites, but you own the URL replacement.
  • Ask the new host. Most managed hosts will migrate you for free. If you're moving to managed hosting specifically, this is usually the best option — it costs nothing and there's someone to escalate to.

Get SSL working at this stage too. Many hosts provision a certificate automatically once DNS points at them, but if you want a genuinely zero-downtime cutover, sort the certificate out beforehand — either through the host's temporary URL or with a DNS-validated certificate.

Phase 3: The URL problem

This is the part that quietly ruins migrations. WordPress stores some settings as serialized data — strings that encode both a value and its length. A naive find-and-replace of your domain across the database changes the value without updating the recorded length, which corrupts those entries. The site loads, but widgets vanish, menus break, and customizer settings reset.

Never do a raw SQL replace on your domain. Use a tool that understands serialized data:

wp search-replace 'https://oldsite.com' 'https://newsite.com' --dry-run
wp search-replace 'https://oldsite.com' 'https://newsite.com'

Always run the --dry-run first and read the summary — it tells you how many tables and rows will change, which is your last chance to catch a typo before it's applied everywhere.

If you don't have command-line access, this is exactly what migration plugins and the Better Search Replace plugin do for you. Either is fine; what matters is that the replacement is serialization-aware.

One note on scope: if you're keeping the same domain, you may not need to replace anything at all. The URLs only change if the domain changes, or if you're moving between a temporary staging URL and the real one.

Phase 4: Test before anyone is affected

Your site is now running on the new host and nobody has been pointed at it. Verify it properly, because this is the only window where a problem is cheap.

To reach the new server under your real domain before DNS points there, either use the host's preview or temporary URL, or edit your own computer's hosts file to map the domain to the new server's IP. Only you are affected, and you see exactly what visitors will see.

Work through:

  • Home page, several inner pages, a single post, and an archive page
  • Images and other media load (a very common failure — check the browser console)
  • wp-admin loads and you can log in
  • Forms submit and arrive
  • Search returns results
  • Any payment flow, including webhooks
  • Site works over HTTPS with no mixed-content warnings

Phase 5: Cut over

Point DNS at the new host — either by updating your A record to the new IP, or by switching nameservers to the new provider. If you lowered the TTL in phase 1, most visitors move across within minutes. Some ISPs ignore TTL regardless, which is why the next phase matters.

If the domain stays the same and your URLs are unchanged, there is nothing else to do for SEO. If any URL structure changed, set up 301 redirects from old to new and update your sitemap.

Phase 6: After the switch

Keep the old host running for 48 to 72 hours. This is your rollback, and it costs a few days of duplicate hosting. Cancel it only once you're confident.

Post-migration checklist:

  • Re-save permalinks (Settings → Permalinks → Save) — clears rewrite rules, fixes sudden 404s
  • Confirm SSL is active and there's no mixed content
  • Test a form submission and, if relevant, a real transaction
  • Confirm scheduled posts publish — WP-Cron behaves differently depending on host configuration
  • Check that analytics and any tag manager are still firing
  • Verify the property in Search Console and resubmit your sitemap
  • Watch for 404s in the first few days and redirect them
  • Only then cancel the old hosting

The email trap

If your email runs on your old host, switching nameservers can take your email with it. This is the single most common migration disaster, and it's invisible until someone notices that enquiries stopped arriving.

Here's the mechanism. If you@yourdomain.com is hosted by your current provider, the MX records that direct your mail live in that provider's DNS. Move the domain to a new host by pointing nameservers, and those MX records are no longer being served — so mail has nowhere to go.

Before you switch anything, find out where your MX records point. Then pick one of these:

  1. Move email to a dedicated provider first (Google Workspace, Microsoft 365, Fastmail). This is the cleanest answer: email stops depending on where your website lives, which is better architecture regardless of migrations.
  2. Migrate DNS records individually rather than switching nameservers wholesale — keep MX, SPF, DKIM and DMARC pointed at the old provider, and change only the records that need to change.
  3. Keep DNS where it is and just update the A record to the new host's IP. Minimal change, minimal risk.

Option 1 is the right answer for almost everyone. It costs a few dollars a month and permanently removes a category of problem. Do it a week before the site migration, confirm mail flows, and then migrate the site with no deadline pressure.

And note what no site backup covers: your email is not in your WordPress backup. It's a separate system with separate retention.

FAQ

How much downtime should I expect?

Minutes of DNS propagation if you follow the sequence above, and zero interruption for most visitors who hit whichever server their resolver already knows about. The migrations that take hours are the ones where DNS is switched first and debugging happens afterwards. Staging the site on the new host and testing it before cutover is the entire difference.

Will migrating hurt my SEO?

Not if the URLs stay the same. Search engines care about URLs, not about which server answers them. Two things do cause damage: changing your URL structure without 301 redirects, and leaving the site in a broken or half-migrated state for hours while crawlers visit. If URL structure has to change, map every old URL to its new one with a 301 and resubmit your sitemap.

Do I need a migration plugin?

It's the accessible option and the right one if you're not comfortable with the command line, mainly because these plugins handle serialized URL replacement correctly. That's the thing you must not get wrong. The alternative is WP-CLI or a migration done by your new host. Most managed hosts will do it for free, and if you're moving to managed hosting, letting them handle it costs you nothing and gives you someone to escalate to.

Why did my email stop working after the move?

Because your MX records were served by your old provider's DNS, and switching nameservers stopped serving them. It's the most common migration failure precisely because it isn't visible on the site itself. Recover by repointing the MX records, or better, move email to a dedicated provider so this dependency disappears permanently.

How long should I keep the old hosting?

48 to 72 hours minimum after cutover. Some ISPs and resolvers ignore low TTL values, so a small share of visitors will still be arriving at the old server for a day or two. If the old site has any dynamic function — orders, form submissions, user signups — those visitors' activity lands on the old server, and you need to be able to reconcile it. A few days of duplicate hosting is cheap insurance.

Can I move just the domain and keep my current host?

Yes, and it's a much smaller job than a full migration — it's a registrar-level change plus a domain configuration update on the host's side. But it still involves serialized URL replacement in the database, so treat it with the same care. And it still affects email if your mail is tied to the domain's DNS.
