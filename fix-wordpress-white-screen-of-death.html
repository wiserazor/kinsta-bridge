How to Fix the WordPress White Screen of Death

A blank page with no error message is the most unnerving WordPress failure there is, because it tells you nothing. This guide walks the diagnosis in the order that actually finds the cause — surface the error first, then rule out memory, plugins, theme and core files — instead of guessing and restoring.

Confirm it's really the white screen

"White screen of death" is a catch-all phrase people use for any blank page, but the fixes differ. Before you start renaming folders, work out which of these you have:

  • Blank page, no error text, admin also blank — a fatal PHP error is being suppressed. This is the classic WSOD.
  • Front end blank, wp-admin works — far more likely your theme than a plugin.
  • Admin blank, front end fine — a plugin doing something expensive or broken inside wp-admin.
  • Blank with a browser error like 500, 502, or 504 — that's a server-level response, not purely a WordPress one. Check your host's error log; the fix may be outside WordPress entirely.
  • Blank on one page only — usually memory exhaustion or a bad query on that specific template, not a global breakage.

Open your browser's developer tools and reload. If the Network tab shows a 200 response with an empty body, it's a PHP fatal. If it shows a 5xx, start with the server.

Back up before you touch anything

Everything below is safe when done in the right order, but "safe" and "impossible to make worse" aren't the same thing. Before you start, make sure you have a copy of two things: the database and the wp-content folder. Those two contain your entire site. The WordPress core files (wp-admin and wp-includes) can always be re-downloaded from wordpress.org, so don't panic about those.

If you can't reach wp-admin, take the backup through your host's file manager, your hosting control panel's backup tool, or over SFTP. If you have no route to either, stop and ask your host for a snapshot before continuing — our backup guide covers why host snapshots are the fastest recovery for exactly this moment.

Step 1: Make WordPress tell you the error

By default WordPress hides fatal errors from visitors, which is good for security and terrible for debugging. Turn logging on so the error goes to a file instead of the screen.

Open wp-config.php (it's in the site root, the same folder as wp-admin) and add these lines above the comment that says /* That's all, stop editing! Happy publishing. */:

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );

Then reload the blank page. WordPress writes the error to /wp-content/debug.log. Open it and read the last few lines — you're looking for a line starting with PHP Fatal error. It will usually name the file that caused it, and that file path tells you which plugin or theme to look at. A path containing /wp-content/plugins/some-plugin/ means you already know the culprit.

Turn this back off when you're done. Leaving debug logging running on a live site fills the log file with notices and, depending on server permissions, can expose file paths. Set those three constants back to false and delete debug.log once the site is working.

This step matters more than the rest because it converts guesswork into a specific answer. Every other step on this page is a way of finding the culprit when you can't get the error.

Step 2: Raise the memory limit (and read the warning)

Exhausted memory is one of the most common causes, and it's the quickest thing to rule out. Add this to wp-config.php, again above the "stop editing" line:

define( 'WP_MEMORY_LIMIT', '256M' );

If that alone doesn't do it, the limit may be capped at the server level rather than by WordPress. Options, in order of preference:

  • Hosting control panel — most managed hosts have a PHP settings screen where memory_limit can be changed without touching files.
  • php.ini or .user.ini — memory_limit = 256M
  • .htaccess — php_value memory_limit 256M. Only works on Apache with mod_php. On nginx, which most managed hosts use, this will throw a 500 error instead. If adding it makes things worse, remove it immediately.
If raising the limit "fixes" it, you haven't fixed it. You've raised the ceiling above a leak. Something — usually a plugin doing an unbounded query, or a theme loading an enormous dataset — is consuming more memory than it should. It will come back the moment your content grows. Treat the memory bump as breathing room, not a cure, and note which page triggered it.

Step 3: Deactivate every plugin at once

Plugin conflicts cause more white screens than anything else. The problem when your site is blank is that you can't reach the Plugins screen — so you deactivate them from the outside.

Connect over SFTP or your host's file manager and rename the plugins folder:

wp-content/plugins  ->  wp-content/plugins.disabled

WordPress can no longer find any plugin, so it treats them all as inactive and your site should load — with features missing, but loading. That confirms it's a plugin.

Now rename it back to plugins and go through them one at a time: rename an individual plugin's folder to disable just that one, reload, and repeat until the white screen returns. The last one you disabled is the culprit.

If you have command-line access, this is faster:

wp plugin deactivate --all

And if you have database access but no file access, you can clear the active plugins list directly:

UPDATE wp_options SET option_value = ''
WHERE option_name = 'active_plugins';

Check your table prefix first — it isn't always wp_. This approach leaves plugin files in place, which makes it the cleaner option on shared hosting where other sites might rely on the same directory.

Step 4: Force a default theme

If disabling all plugins didn't help, or if only the front end was blank, it's the theme. Same principle: rename the active theme's folder inside wp-content/themes/ and WordPress falls back to a bundled default theme such as Twenty Twenty-Four.

If it falls back to a theme you don't have installed, WordPress will error instead. To be safe, set it explicitly in the database:

UPDATE wp_options SET option_value = 'twentytwentyfour'
WHERE option_name IN ('template','stylesheet');

Your theme's customizer settings, widget placements and menu assignments live in the database, so renaming a folder doesn't destroy them — they'll be waiting when you switch back. What you will lose is any change you made by editing theme files directly, which is exactly why child themes exist.

Step 5: Replace the WordPress core files

If neither plugins nor theme is responsible, core files may be corrupt — a failed automatic update, an interrupted file transfer, or a partial restore.

Download a fresh copy of WordPress from wordpress.org, unzip it, and upload only the wp-admin and wp-includes folders, overwriting what's there. Then re-upload the individual root files from the fresh download (such as index.php and wp-load.php) — but not wp-config.php, which is yours and contains your database credentials.

Never overwrite wp-content. That folder holds your themes, plugins, uploads and custom code. Replacing it with the stock version from wordpress.org deletes your site. If a guide ever tells you to replace it wholesale, it's wrong.

Step 6: Check PHP version compatibility

A white screen that appears right after your host upgraded PHP — or right after you did — is almost always a plugin or theme calling a function that was removed in the newer version. PHP 8.x removed and changed a good deal of behaviour that older code relied on.

The fix is to find the offending plugin (step 3 will surface it), update it, and if no update exists, replace it. Running an abandoned plugin on a modern PHP version is a slow-motion version of the same problem; it will break eventually. If your host lets you switch PHP versions, rolling back temporarily is a legitimate way to buy time — just don't leave it there permanently, since old PHP branches stop receiving security patches.

Symptom triage table

When you just want the fastest path, match your symptom:

SymptomMost likely causeTry this first
Blank everywhere, including adminPlugin fatal errorRename the plugins folder
Front end blank, admin fineTheme fatal errorRename the active theme folder
Admin blank, front end finePlugin misbehaving in wp-adminRename the plugins folder
Blank immediately after an updateVersion incompatibilityDisable the thing you just updated
Blank right after editing codeSyntax errorRestore that file from backup
Blank on one page onlyMemory or a slow queryRaise memory, then profile that template
Message about exhausted memory sizeMemory limit, or a leakRaise the limit, then find the leak
Blank plus a 500 status codeServer-level errorCheck the host's error log
Blank after changing PHP versionDeprecated function callIdentify and replace the outdated plugin
The order matters. Working top to bottom — get the error, rule out memory, disable plugins, force a theme, replace core — costs about fifteen minutes and identifies the cause in nearly every case. Jumping straight to "restore from backup" works too, but you learn nothing, and the next occurrence is just as mysterious as the first.

FAQ

Will enabling WP_DEBUG show errors to my visitors?

Not with the settings above. Setting WP_DEBUG_DISPLAY to false sends errors to the debug.log file rather than to the browser, so visitors see the same blank page they did before. That's the point: you get the information without exposing file paths and stack traces to the public.

Can I fix this if I can't access FTP or my host's file manager?

Yes, if you have database access through something like phpMyAdmin. Disabling plugins and switching themes can both be done with the SQL statements above. If you have neither file nor database access, contact your host. This is a routine request for them, and a host that won't help you recover a blank site is worth reconsidering next time you compare providers.

Why did it happen right after I updated something?

Because the update changed code that your theme or another plugin depended on. It's rarely malicious and usually specific: one function signature changed, or one file moved. The reliable fix is to identify the outdated component, then update or replace it, rather than avoiding updates altogether. Skipping updates trades a visible break now for an invisible security hole later.

Is it always a plugin?

No. In rough order of likelihood it's a plugin, then a theme, then memory exhaustion, then a PHP version mismatch, then corrupted core files. That's also the order to work through, because each check is cheap and the early ones catch most cases.

Will fixing the white screen lose my content?

It shouldn't. Posts, pages, media and settings live in the database and in wp-content, and none of the steps above delete either — renaming a folder doesn't remove it. That said, take a backup before you start. The one scenario where you can lose data is overwriting wp-content with a fresh WordPress download, which is why the instructions above deliberately exclude it.

My site is back but I never found the cause. Is that OK?

It's survivable but not ideal. If you resolved it by disabling everything and re-enabling selectively, you at least know which component it was. If it resolved itself after a memory bump, assume it will return. In that case keep debug logging enabled for a few days and check the log after your next traffic spike.
