Why WooCommerce changes the hosting math

A normal WordPress page is cached and served as a static file to everyone. WooCommerce breaks that model: a customer with items in their cart is logged in, and logged-in pages can't be served from a generic page cache. That means the database, PHP, and object cache do the heavy lifting on every request — exactly the parts budget shared hosting skimps on. If your origin is slow, no CDN trickery fully hides it, because the cart and checkout are dynamic by nature.

So the questions for a store owner aren't "how cheap" or "how fast is the blog." They're: how fast is the checkout when fifty people are browsing at once? Does object caching actually work for cart sessions? Can I stage a price change safely? And who picks up when the payment gateway times out on Black Friday?

Caching & the logged-in problem

Full-page caching is why brochure sites are fast on cheap hosting. But WooCommerce marks cart, checkout, and account pages as "do not cache" — they're unique per visitor. So performance for a store depends on three layers a budget host often lacks or bolts on poorly:

  • Object cache (Redis / memcached): caches database query results so product lookups and cart calculations don't hit the database on every request. This is the single biggest win for WooCommerce.
  • PHP worker count: concurrent requests (browsing + checkout) are handled by PHP workers. Too few and checkout queues during a traffic spike. Kinsta and WP Engine size these per plan; Cloudways lets you scale the server.
  • CDN for static assets: product images, CSS, JS — offloaded close to the visitor. Helps, but doesn't touch the dynamic checkout.

The takeaway: judge a host for WooCommerce by its origin performance and object caching, not by a cached-blog speed test someone screenshotted.

What to measure (not just homepage speed)

Almost every hosting review you'll read benchmarks a logged-out homepage. For a store that number is close to meaningless — it measures the CDN, not the checkout. If you want to know whether a host can handle your store, these are the four numbers that actually predict revenue:

  • TTFB on a logged-in cart page. Log in, add a product, and load the cart. That request can't be served from a page cache, so it exercises PHP, the database, and your object cache. This is your floor.
  • Checkout time under concurrency. Twenty people browsing is a different problem from twenty people checking out. Run a modest concurrent test (20–50 virtual users) against cart and checkout, not the homepage, and watch whether response times hold flat or climb.
  • Object cache hit rate. If Redis or memcached is configured, a healthy store should be hitting cache on the large majority of queries. A low hit rate usually means the cache is too small or a plugin is bypassing it.
  • Admin responsiveness. WooCommerce's order and product screens are database-heavy. If saving an edit or filtering orders takes five seconds, your origin is struggling — and that same strain shows up at checkout during a sale.
Before you load-test: don't fire aggressive traffic at a host you don't have an account with, and check the acceptable-use policy of any host you're already on — some treat unannounced load testing as abuse and will throttle or suspend you. The safe path is to test inside your own money-back window on a staging clone, at modest concurrency, and to tell support what you're doing if you plan to push hard.

One more honest caveat: published benchmark numbers age badly. Hosts change infrastructure, plans, and PHP versions constantly, and a single-site test says more about that site's plugins than about the platform. Treat any third-party benchmark — including ours — as a starting hypothesis, then verify on your own store during the trial window.

Kinsta for stores

Kinsta's container isolation keeps PHP workers dedicated to your site, so a traffic spike on a neighbor can't steal your checkout capacity. For stores, the relevant notes:

  • Redis object cache is a $100/mo account add-on — relevant once your store is busy enough that query caching pays for itself.
  • Staging lets you test a WooCommerce or plugin update on a clone before pushing to live — critical when a bad update can break checkout.
  • Free migrations bring an existing store over, including a staging check before you flip DNS.
  • Engineer-level 24/7 support — the 9 p.m. payment-gateway question goes to someone who knows WordPress, not a script.

Pros: Predictable origin performance under load; isolated containers; smooth staging; strong support.

Cons: Redis is a paid add-on; visit caps need monitoring; entry price higher than Cloudways/SiteGround.

Cloudways, WP Engine, SiteGround & hosting.com for stores

Cloudways

Cloudways gives you a managed stack on the cloud you pick (DigitalOcean, AWS, Google Cloud) with object caching available at the server level. For stores, the appeal is control and cost: you can scale the server as order volume grows, and you're not paying a per-site premium for capacity you haven't grown into yet. The trade-off is that tuning is on you — or on your developer.

Store-relevant notes

  • Object caching: available at the server level rather than as a per-site paid add-on, which changes the cost math materially for a busy store.
  • Vertical scaling: resize the server as traffic grows without rebuilding anything.
  • Staging per application: clone the store, test a WooCommerce or payment-plugin update, then push live.
  • Bandwidth is metered: image-heavy catalogs can push you into overages — worth modelling before you commit.

Pros: Low entry price; choose your cloud; scale the server as the store grows; object caching without a per-site add-on.

Cons: More tuning on you; bandwidth overages can surprise image-heavy catalogs; steeper learning curve than fully managed.

WP Engine

WP Engine's proprietary EverCache and enterprise posture suit larger, brand-name stores with compliance and governance needs. It's a mature platform with mature processes — which is exactly what a regulated business wants and exactly what a two-person store doesn't need. The two things to check before committing are the plugin policy and the price at renewal.

Store-relevant notes

  • EverCache: a proprietary caching layer tuned for WordPress, handling much of the tuning for you.
  • Plugin policy: some plugins — including certain caching and WooCommerce extensions — are restricted or discouraged. Audit your must-have extensions against their list before you migrate.
  • Governance: audit trails and enterprise-grade process, which matters if procurement or compliance is involved.

Pros: Enterprise trust; mature staging; proprietary caching tuned for WordPress; governance features.

Cons: Pricier at entry; stricter plugin policies; overkill for a small store.

SiteGround

SiteGround's dynamic cache and memcached work well for smaller stores just getting started, at the friendliest entry price. If you're under ~50 products and not yet high-traffic, it's a sane on-ramp — the support is genuinely good, which counts for a lot when you're learning WooCommerce. The ceiling is the issue: shared resources mean a neighbour's spike can affect you, and renewal pricing rises well above the intro rate.

Store-relevant notes

  • Dynamic cache + memcached: handles the object-caching basics without you configuring Redis by hand.
  • Support quality: consistently the strongest point for non-technical owners.
  • Shared resources: plan your exit before a big campaign, not during it.
  • Renewal pricing: read the renewal rate, not just the intro rate, when you do the maths.

Pros: Lowest first-term cost; excellent support; beginner-friendly; caching basics handled.

Cons: Shared resources (noisy-neighbor risk at scale); renewal prices jump significantly; not built for high-concurrency checkout.

FAQ

Do I need Redis for a small store?

Not at first. A small store on SiteGround or Cloudways with built-in object caching is fine. Add Redis (or a paid object-cache add-on) once query load grows — usually when you're past a few hundred concurrent shoppers or a slow admin.

Is a CDN enough to speed up checkout?

Partly. A CDN accelerates static assets (images, scripts) but not the dynamic cart and checkout, which are served from origin. The origin's PHP workers and object cache still decide checkout speed.

Can I stage a WooCommerce update safely?

Yes on all five managed hosts — one-click staging lets you clone the store, apply the update, and push to live after testing. Never update WooCommerce or payment plugins directly on a live store.

Does hosting affect PCI compliance?

Hosting is one layer; your store's payment flow matters more. Using a hosted payment gateway (Stripe, PayPal) keeps card data off your server, which simplifies compliance regardless of host. Verify your gateway's requirements.

What if my store outgrows the plan?

All five let you scale up without a migration weekend — that's the point of managed hosting. Watch PHP-worker saturation and visit counts in the dashboard, and step up a tier before a campaign peaks.

Can I just run WooCommerce on cheap shared hosting?

You can, and many stores start there. The constraint isn't whether it works — it's what happens under concurrency. Shared plans give you a small, shared pool of PHP workers, so a burst of simultaneous checkouts queues behind each other. If you're doing a handful of orders a day, that never bites. If you're running paid traffic to a sale, it's the most expensive place to save money.

Will a faster host fix my slow store?

Sometimes. If the bottleneck is server capacity — checkout queues during traffic, slow admin under load — then yes, better hosting is the fix. If the bottleneck is your own site (unoptimised product images, a heavy page builder, nine plugins doing the job of two), a faster server masks it briefly and then the bloat catches up. Diagnose before you spend: run the store through a profiler, fix the obvious wins, and then judge whether the host is actually the problem.

Should the store and the marketing site live on the same host?

Usually yes — one dashboard, one bill, one support contact, and modern managed hosts isolate sites from each other. Splitting them adds operational overhead that only makes sense at real scale, or when the store has compliance requirements the marketing site doesn't. If you do keep them together, make sure they're separate installations, not one WordPress multisite carrying both.
